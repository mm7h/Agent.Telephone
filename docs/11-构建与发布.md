# 构建与 GitHub 发布

本项目使用 .NET 8、NuGet 中央包管理及手动 GitHub Actions 发布。Release 附件是电话服务运行包，支持 `win-x64`、`win-arm64`、`linux-x64`、`linux-arm64`。

## 本地开发与依赖管理

仓库根目录的三个文件分别负责：

| 文件 | 职责 |
| --- | --- |
| `Directory.Packages.props` | 集中声明直接 NuGet 依赖版本；各项目仅声明无版本的 `PackageReference`。 |
| `Directory.Build.props` | .NET 8、可空类型、隐式 using、作者、仓库地址和默认版本 `0.1.0`。 |
| `Directory.Build.targets` | 类库包图标、宿主外置配置，以及显式启用的运行包发布规则。 |

新增依赖时，在项目中添加 `PackageReference`，并在中央文件中添加对应的 `PackageVersion`。测试适配器的 `PrivateAssets` 和项目特有设置继续由项目文件维护。SQLite 各项目统一使用 `10.0.13`。

```powershell
dotnet restore Agent.Telephone.sln
dotnet build Agent.Telephone.sln -c Debug --no-restore
dotnet test Agent.Telephone.sln -c Debug --no-build
dotnet build Agent.Telephone.sln -c Release --no-restore
dotnet test Agent.Telephone.sln -c Release --no-build
```

普通构建保留 SDK 默认行为。运行包发布使用 `ReleasePackage=true`，启用自包含单文件和原生库解压加载，关闭裁剪与 ReadyToRun。

Linux 首次构建前需安装 `patchelf`（Ubuntu：`sudo apt-get update && sudo apt-get install -y patchelf`）。普通可运行宿主及测试宿主在构建后也会隔离 Sherpa 的 ONNX Runtime 副本，避免其与 Microsoft ONNX Runtime 的同名原生库冲突；NuGet 缓存保持不变。Linux 上执行 Codex 进程集成测试还需 `pwsh`（PowerShell 7），GitHub runner 已提供。

## 本地生成运行包

需要 .NET 8 SDK、PowerShell 7、Python 3.11+、Git；Linux 还需安装 `patchelf`。在匹配目标系统及 CPU 架构的机器上运行，例如 Windows x64：

```powershell
pwsh -NoProfile -File .github/workflows/scripts/Publish-Release.ps1 `
  -RuntimeIdentifier win-x64 -Version 0.2.0-rc.1 -ReleaseTag v0.2.0-rc.1 `
  -OutputDirectory artifacts/local-release
```

Linux 上相同命令使用 `linux-x64` 或 `linux-arm64`。Windows ARM64 使用 ARM64 系统及原生 ARM64 .NET SDK。发布脚本在与目标系统、架构对应的机器上运行，与 GitHub runner 的组织方式一致。

脚本还接受 `SourceDirectory` 和 `SourceCommit`；声明的提交必须等于源码 checkout 的 HEAD。版本由 tag 去掉可选的小写 `v` 得到；程序集版本为 `major.minor.patch.0`，信息版本保留预发布后缀，三个数值段均不得超过 65534。支持 `[v]major.minor.patch[-prerelease]`，不支持 `+build` 后缀。

本地有未提交源码时，生成的包仅适合本地验证；可追溯的发行包由 GitHub 的干净 checkout 构建。为避免覆盖，输出目录已有同名 ZIP 时脚本会失败，重试请选择新的输出目录。

生成的文件为：

```text
Agent.Telephone-0.2.0-rc.1-win-x64.zip
Agent.Telephone-0.2.0-rc.1-win-x64.zip.sha256
```

ZIP 根目录包含服务程序、可编辑 `configs/`、部署文档、许可证、空的资源/数据目录，以及记录源码和程序集版本的两份元数据。发布脚本仅复制受版本管理的文档、指定配置与提示词；不递归复制本地运行目录。FFmpeg、模型、Codex CLI 均需另行安装或下载。

Linux 上会从 Sherpa NuGet 包复制并重命名其 ONNX Runtime，使用 `patchelf` 修改副本的依赖及搜索路径，避免同名原生库冲突；不会修改 NuGet 缓存。

生成运行包后，完整部署仍需准备资源、凭据并完成 HT701 通话验收。

## 在 GitHub 填写 tag 并创建草稿

1. 将工作流、脚本和构建配置一并合入仓库**默认分支**。GitHub 要求默认分支存在手动工作流，才会提供正常的手动运行入口。
2. 打开 **Actions → Release packages → Run workflow**。
3. 选择源码分支，在 `tag` 填入如 `v0.2.0` 或 `v0.2.0-rc.1`；按需勾选 `prerelease`。
4. 工作流完成后，从运行摘要打开 Release 草稿，检查四个平台 ZIP、四个 `.sha256` 和 `SHA256SUMS`。
5. 先使用新的 `rc` tag 验证部署和真实通话，再点击 **Publish release** 公开草稿。

tag 不存在时，准备任务会在所选分支本次运行的提交创建 tag。tag 已存在时，构建其实际指向的提交，包括 annotated tag；不会把它移动到分支最新提交。分支在任务排队后继续更新，也不会改变本次构建的源码 SHA。

发布工作流只接受手动运行；推送 tag 不会启动发布。普通分支 push 和 PR 会触发独立的 Windows/Linux x64 构建测试。发布时四个平台各自运行全量测试；任一平台失败，都不会进入草稿上传任务。

带预发布后缀的 tag 自动标记为预发布。`prerelease` 控制新草稿；重跑已有草稿时保留已编辑的名称、说明、预发布属性及其他人工附件，仅替换本次管理的同名附件。

默认使用仓库提供的 `GITHUB_TOKEN`，无需 NuGet API Key 或个人访问令牌。只有准备 tag 和草稿上传任务申请 `contents: write`。若仓库或组织策略禁止写入，需由仓库管理员调整相应策略。

## 失败重试与校验

- 测试或构建失败：检查对应平台日志和 diagnostics artifact；准备阶段已创建的 tag 会保留。源码修复后使用新 tag，避免把旧 tag 误当成最新分支源码。
- 下载或上传中断：源码未变时可重跑同一工作流，补齐同 tag 的未公开草稿。
- tag 被移动或 Release 已公开：任务拒绝继续写入；公开版本请使用新 tag。
- 所有包会校验 SHA256、PE/ELF 架构、必需文件、空资源目录、程序集版本和源码记录，齐全后才会上传。

Windows 可运行 `Get-FileHash <zip路径> -Algorithm SHA256`；Linux 可运行 `sha256sum -c SHA256SUMS`。检查通过后，按 [快速开始与部署](00-快速开始与部署.md) 配置资源并启动服务。

Linux 运行包在 Ubuntu 24.04 runner 上构建，使用 glibc，不支持 Alpine/musl。自包含程序仍需要系统基础库。解压后执行 `chmod +x ./Agent.Telephone.Sample.Server`，从解压目录启动；systemd 配置正确的 `WorkingDirectory` 和可写的 `DOTNET_BUNDLE_EXTRACT_BASE_DIR`。
